Project Overview — What & Why

The problem being simulated, the solution built, and the exact boundary of scope.

In high-throughput distributed systems thousands of clients hit the same endpoints concurrently. Without control you get resource exhaustion, DoS, credential stuffing, bot scraping and unfair usage. Production gateways (Kong, AWS API Gateway, NGINX, Cloudflare) solve this with metering + policy + anomaly engines.

This project rebuilds that internal logical behaviour as a desktop app: every request is an object, every rule is a policy object, every verdict is a report — all executed in memory with the Java Time API and collections.

Mandatory features delivered: register API clients → record simulated requests → apply rate-limit policies → detect excessive requests inside time windows → generate a per-client abuse report.

🎯Core Objective

Track client request activity → apply rate-limiting rules → detect abnormal/abusive patterns → generate a per-client usage & violation report.

🧠Core OOP Concepts

Domain modelling, encapsulation of counters/thresholds, polymorphic policy evaluation, Strategy-like design, type-safe Enums.

⚡Zero Overhead

No sockets, no latency, no external infra. 100% in-memory with Map/List, LocalDateTime and Duration.

📊Visual Analytics

Reactive dark-mode JavaFX dashboard: metric cards, live line chart, bar chart, sortable activity table, console log, report dialogs.

🔌Pluggable Engine

5 interchangeable RatePolicy implementations hot-swapped at runtime through one unified evaluate() contract.

🗃Persistent CSV

Clients, services and full request logs survive restarts through data/*.csv with automatic reload on boot.

🕑Threading model

Everything — ingestion, policy evaluation, CSV write, UI refresh — runs on the single JavaFX Application Thread. No worker threads: a burst of 20 requests is processed synchronously inside one button click.

While idle, only statusTimer fires every second: recompute remaining quota, getTimeUntilReset(), risk badge and block countdown, then repaint.

💾State on restart

loadFromCsv() replays data/requests.csv through restoreFromLogEntries(), so the table, charts and tracker are repopulated before the window is shown.

4.5  Four Ingestion Modes

🖱A — Manual interactive form

handleSendRequest(clientId, type, logPanel, onUpdated) — type is randomized when null, and ALL_CLIENTS replays the same pipeline for every registered client.

💥B — High-velocity burst

generateBurst(clientId, 20, 10s) builds evenly spaced timestamps, then feeds them through processRequest() one by one: the first ~10 pass, the rest trip the cooldown.

📁C — Dataset import

DatasetLoader.loadFromFile / loadFromText accepts comma, semicolon or space separators, skips # comments and headers, and stores bad rows in getErrors() instead of aborting.

🔗D — Multi-service fan-out

sendRequest(ids, type) issues one request per service with an isolated quota key svc_<id> and returns a LinkedHashMap in selection order.

Rate-Limit & Abuse Policies (Strategy Engine)

Five algorithms behind one RatePolicy interface — boot defaults taken straight from EnhancedDashboardView:54–60, the exact trigger math of every detector, and the monotonic severity ladder that feeds the risk score.

⏱ FixedWindowPolicy

→ WARNING

Counts requests falling inside a discrete window ending at the latest request timestamp.

count = |{ r : 0 ≤ latest - r.t ≤ W }|
count > max → addViolation() + setLevel(WARNING)
  • Boot default: max 5 / window 3s — strict > means it trips on the 6th request
  • Low memory, but a burst straddling two windows can slip through
policy/FixedWindowPolicy.java

🔄 SlidingWindowPolicy

→ CRITICAL

Pair scan over every continuous interval — kills boundary-burst exploits.

for start i: count = 1; for j > i: Δt = t(j) - t(i)
if Δt ≤ W: count++ → count > max → addViolation + CRITICAL
  • Boot default: max 5 / window 3s — trips on the 6th request in any window
  • Escalates straight to CRITICAL and stops scanning; the other 4 policies still run but can never lower the level
policy/SlidingWindowPolicy.java

💥 BurstDetectionPolicy

≥1 WARN ≥3 CRIT

Finds clusters of rapid-fire requests — models DoS spikes and flash mobs.

for start i: scan forward while t - t(i) ≤ 3s (breaks on first larger gap)
count ≥ 4 → burst++ + violation
bursts ≥ 3 → CRITICAL · bursts ≥ 1 → WARNING (only from NORMAL)
  • Boot default: ≥4 requests in 3 seconds (4, 3s)
  • One violation per burst start, timestamped HH:mm:ss; multiple overlapping starts multiply the count
policy/BurstDetectionPolicy.java

🧠 AbnormalPatternPolicy

WARN CRIT

Three statistical heuristics that unmask automated scripts and bots.

① hour ∈ [02:00, 05:00) & count > 3 → WARNING
② one request type > 90% of ≥10 req → scraping
③ |Δs[i] - Δs[i+1]| ≤ 1s for >70% of ≥10 req → CRITICAL bot
  • detectOffHoursActivity() · detectRequestTypeImbalance() · detectUniformIntervals()
  • Needs ≥5 requests to build the interval array; the bot verdict sets CRITICAL unconditionally (not guarded by NORMAL)
policy/AbnormalPatternPolicy.java

🔅 RetryAbusePolicy

WARN CRIT

Detects aggressive re-attempts following rejected calls.

① gaps < 1000ms counted across the log; count > 5 → CRITICAL
② longest run of gaps ≤ 2s; ≥ 8 → WARNING (only from NORMAL)
  • Boot default: (8 consecutive, 2s window)
  • detectRapidRetries() hammers sub-second · detectSuspiciousRapidRequests() resets its streak on the first slow gap
policy/RetryAbusePolicy.java

◆ RatePolicy — the Strategy contract

1 interface

One abstract method plus four defaults — every detector drops into the same slot.

abstract evaluate(RequestLog, AbuseReport)
default evaluate(Client) · evaluate(Client, RequestLog, AbuseReport)
default getName() → class simple name · getDescription()
  • policy imports model only — zero awareness of service or ui
  • Registered order: Fixed → Sliding → Burst → Abnormal → Retry
policy/RatePolicy.java · interface

🔍 RateLimitAnalyzer — the 10-second lens

5 policies

Before judging anything it trims the log to the last 10 seconds, then runs every policy over that slice.

recent = { r : now - r.t ≤ 10s }
if recent is empty → return a clean AbuseReport
else for p in policies: p.evaluate(filteredLog, report)
  • Called once per click — DashboardActionHandler:630,666 → analyze(log).getLevel()
  • addViolation() drops duplicates and blank messages, so repeated identical hits never inflate the risk score
service/RateLimitAnalyzer.java

🏁 Severity Escalation Ladder

NORMAL → WARNING → CRITICAL
setLevel(): CRITICAL is final · CRITICAL→WARNING and WARNING→NORMAL are dropped
riskScore = min(100, violations×15 + WARN 20 / CRIT 40)
  • getRiskScore() drives the dashboard risk badge · 0 when there are no violations
  • isMoreSevereThan() compares ordinal() of NORMAL / WARNING / CRITICAL

Setup, Build & Run Guide

From clone to running app in five commands. Coordinates com.runtime_crew:api-ratelimit-simulator:1.0 — Maven-only (no mvnw, no shell/batch scripts, no Makefile), verified here with Maven 3.9.16.

$git clone https://github.com/With-ALIF/api-ratelimit-simulator.git
$cd api-ratelimit-simulator
$mvn clean test
$mvn javafx:run
$mvn clean package
What pom.xml (61 lines) actually declares

Java release 17 · 3 deps: javafx-controls + javafx-fxml (21.0.2, compile) and junit-jupiter (5.10.2, test) · 2 plugins: maven-compiler-plugin 3.15.0 (-Xlint:all, showWarnings) and javafx-maven-plugin 0.0.8 with mainClass=com.smartratelimit_abuse.MainApp. No repositories, no profiles, no shade/assembly plugin.

The JAR is not executable

mvn clean package writes target/api-ratelimit-simulator-1.0.jar — a plain jar with no Main-Class manifest, so java -jar will not launch the app. The supported run path is mvn javafx:run (the goal comes from the CLI; the POM only pins the plugin version).

Runtime files

data/*.csv (requests, multi-requests, clients, services) are gitignored and auto-created on first run; sample_data/ must exist because DatasetLoaderTest reads it from the Maven basedir.

FAQ & Troubleshooting

Questions that come up in demos, viva and first-time setup.

Does this app make any real network calls?

No. There are zero sockets, HTTP clients or servers. Every request is a Java object processed in memory with collections and the Java Time API.

Why did my 6th request get blocked?

The enforcer admits at most maxRequests (10 at boot) inside its 3-second window — once the recent count reaches the max, shouldBlock() returns true and starts the 3-second cooldown. The five policies judge separately at their own thresholds (5 per 3 s for Fixed/Sliding) and only raise severity, they never admit or block.

Why is my risk stuck at CRITICAL?

Severity is monotonic by design. AbuseReport.setLevel() refuses to move from CRITICAL to WARNING or NORMAL, so a later benign check cannot erase an earlier critical finding.

Which policy should I select for a demo?

Sliding Window for the strict-limit story, Burst Detection for the DoS story, Abnormal Pattern for the bot/scraping story. Use a burst of 20 requests to show ALLOWED→BLOCKED within seconds.

Where are my data files? They disappeared from git.

Runtime CSVs under data/ are intentionally untracked since the 2026-09-20 timeline entry (.gitignore → data/*.csv). They are re-created with defaults on the next launch.

mvn javafx:run fails — what do I check?

Confirm java -version is 17+, mvn -v is 3.8+, and you are in the project root (where pom.xml lives). Then mvn clean test before running.

Window shows no charts / old data after restart.

Logs reload from data/requests.csv and data/multi_requests.csv. Delete those files if you want a clean slate, then restart.

Can I change the rate limits without recompiling?

Yes — open Settings in the control panel to change max requests, window, block duration and burst parameters, then save. The enforcer and generator are rebuilt from those values.

How do multi-service quotas stay independent?

Each service is keyed as svc_<serviceId> inside the enforcer, so Facebook and Instagram never share a counter even when one client calls both.

  • FixedWindowPolicy → WARNING  ·  SlidingWindowPolicy → CRITICAL
